Bug 3 — fixed

root cause  Multi-product messages went through the LLM's own product_names array with no deterministic backstop. When that array only surfaced one of two clearly-named products (a casing mismatch, or the LLM simply not noticing both), the second product vanished from the reply with zero trace — reproduced identically whether the LLM was live or rate-limited, so it wasn't an availability fluke.

Deterministic longest-match scan for every real product named in the text

Fix: independently scan the raw query for every real catalog product name, using the same "prefer the longest/most-complete match" rule as Bug 1 — a shorter name only counts as a separate mention if it appears somewhere the longer name's match doesn't already cover. Union this with whatever the LLM found. Anything the LLM named but couldn't resolve to a real product now gets an explicit "couldn't find X" line instead of silently disappearing.

Bug 4 — fixed, verified across the full catalog

root cause  The size filter was 100% digit-based. Any size distinguished by a letter/code with no dimensions (MELODY's "A"–"E") or by a trailing shape qualifier on otherwise-identical dimensions ("240x120x74h" vs "240x120x74h sag") couldn't be selected at all — and a query with bare/space-separated numbers and no literal "x" ("premier wood 240 120", "ritz lounge 140") wasn't recognized as a size at all either.

Scoped it first, as asked, before touching the matching logic: scanned every product in the catalog for this exact shape of ambiguity.

Bare-number size fallback + letter/qualifier disambiguation, both scoped to real catalog vocabulary

Two additive fixes: (1) when no "x"-joined size is found, fall back to any bare 2–3 digit numbers in the query, reusing the same real-dimension matching already in place. (2) independently pull the non-numeric code/qualifier words out of each real size string (stripping pure units like "h"/"x"/"ø") and match them against the query — narrowing to whichever subset matches, not requiring a clean single match, since a bare "sag" legitimately matches two different sag variants at different base sizes. Single-letter codes that double as English words ("a", "i") only count when they're positionally right after the product name or a word like "size"/"style" — never from bare presence alone, so "give me a price for..." can't misfire.

Feature 5 — added, and it fired for real during this exact test session

A short note is now appended to the reply, and a degraded: true flag set on the response, any time the LLM step genuinely failed (bad key, network error, timeout, rate limit) rather than successfully running and just being unsure. This didn't need to be simulated to verify — the Groq free-tier key's 100,000 token/day quota was still exhausted from Round 1 and stayed exhausted for this entire round, so literally every one of the 246 live calls made during this fix-and-verify session carried the note.

What's genuinely still open

Not fixed this round, shown rather than silently left out.

One typo combination still can't be recovered without a live LLM "...greta wood pelle and wlima pelle glove" — the deterministic multi-product scanner (Bug 3's fix) can only find real product names verbatim in the text, so it can't guess that "wlima" means WILMA on its own. With the LLM available it should resolve via the same union logic that already recovered "italia"/"italia couture" and the 4 new combinations — but Groq's quota stayed exhausted for the entirety of this session, so that specific path couldn't be re-verified live this round. The fix is structurally additive (union of LLM guesses + deterministic scan), so it can only help once quota resets, never regress.
A handful of size-collision cases can only narrow to 2, not all the way to 1 Where a product has more than one genuinely different variant sharing the same qualifier word (e.g. two different "sag" sizes at different base dimensions, or "T"-prefixed vs plain across 3 different diameters), the fix correctly excludes everything that doesn't match but can't fully choose between the remaining real options without the user also giving the base size. Safe — never guesses, just shows the real narrowed set.
